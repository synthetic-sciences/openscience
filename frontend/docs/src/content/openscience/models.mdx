OpenScience is model-agnostic. Routing happens on your machine and model calls go directly to the provider or local endpoint you select.

## Connect a provider

Use **Customize → Models** or the CLI:

```bash
openscience keys add
openscience keys list
openscience models
```

You can sign in where a provider supports OAuth or save an API key locally. Environment variables work too:

```bash
export ANTHROPIC_API_KEY=sk-ant-...   # or OPENAI_API_KEY, GEMINI_API_KEY, ...
openscience
```

Anthropic, OpenAI, Google, OpenRouter, Groq, Mistral, xAI, Meta, DeepSeek, and many other providers use the same local flow. The catalog is backed by models.dev and refreshed periodically.

## Local models

OpenScience talks to OpenAI-compatible endpoints on your machine, including Ollama, LM Studio, llama.cpp, and vLLM:

```bash
openscience local add
openscience run --model ollama/llama3.1 "hello"
```

See **[Local models](/openscience/local-models)** for setup details.

## Choose a model per run

```bash
openscience run --model anthropic/claude-opus-5 --variant xhigh "Design the ablation study"
openscience run --model openai/gpt-5.6-terra --variant max "Review the analysis"
openscience run --model moonshotai/kimi-k3 "Implement the pipeline"
```

`--model <provider>/<model>` overrides the default for one run. `--variant` selects a provider-supported reasoning tier such as `minimal`, `high`, `xhigh`, or `max`.

## Route ownership

| Route | Where requests go | Account used |
| --- | --- | --- |
| Provider key | Directly to that provider | Your provider account |
| Provider OAuth | Directly through that provider's supported sign-in | Your subscription or provider account |
| Local model | Your local endpoint | None |

## Key hygiene

Credentials are stored per user in the local data root, never in a project's `.openscience/` directory. General kernels receive a minimal environment, provider-shaped secrets are redacted from output, and retired proxy routes are rejected before a request can carry a user key.
