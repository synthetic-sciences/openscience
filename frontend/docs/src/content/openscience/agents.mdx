**Research** is the default agent. It can search the literature, analyze data, write code, run experiments, and prepare a report. Skills supply procedures for particular domains.

Start with a clear goal, the inputs, an output location, and any limits on time or spending.

## Plan before execution

Use `/plan` when you want to agree on an approach before implementation:

```text
/plan Compare these treatment groups. Identify assumptions, possible
confounders, the statistical test, and the outputs we should save.
```

Plan mode inspects the available material and prepares a plan. It does not carry out the proposed analysis or edit project files, apart from its plan files. After reviewing the plan, return to Research and ask it to execute the agreed steps.

## Normal and Ultra effort

| Effort | Use it for |
| --- | --- |
| Normal | Focused questions, a known analysis, or a small implementation. |
| Ultra | Investigations where comparing additional approaches could change the conclusion. |

Ultra can involve more work and model usage. It does not guarantee a better answer or a fixed number of parallel workers.

```bash
openscience run --effort normal "Check the assumptions in results/analysis.md"
openscience run --effort ultra "Compare defensible approaches to the missing data in this project"
```

A model's reasoning tier is a separate setting; see [Models](/openscience/models).

## Delegation and independence

In the research controls, delegation determines how readily OpenScience divides independent work:

| Delegation | Behavior |
| --- | --- |
| Off | Keep the task with the lead agent. |
| Auto | Delegate when separate work would help. |
| High | Prefer more delegation when the task can benefit from it. |

**Independence** controls how often the agent asks you to resolve choices:

- **Interactive:** plan together and discuss consequential choices.
- **Balanced:** ask about meaningful ambiguities while continuing routine work.
- **Independent:** proceed within the task's constraints and ask when blocked.

These settings guide collaboration. They do not replace your action-approval settings or a service's spending controls.

### Workers

The built-in workers are `explore` (a read-only scout for files, data, code and papers), five specialists built from one template: `ml`, `biology`, `physics`, `chemistry` and `data` (pipelines, processing, coding, visualization), and `general`, a plain worker for a multi-step brief that fits no specialty. Each specialist carries an index of its skill categories and the domain tools those need; the lead dispatches one by name through the Task tool, and independent workers run at the same time with no fixed cap.

You can also hand a job to a worker yourself: type `@` in the composer and pick one (`@explore where is the early-stopping split decided?`). The message becomes that worker's brief, the lead waits for its report, and the worker's session opens from the delegation row. A worker's config can set `hidden: true` to keep it out of the `@` menu while the lead may still dispatch it.

In **Settings → General → Subagents**, choose **Same as calling agent** (the default) or one model for delegated tasks. This policy takes precedence over a specialist profile's model. This is the saved model policy for delegated work; **Same as calling agent** also overrides older saved worker-model preferences. The CLI option `openscience run --worker-model provider/model` explicitly overrides that policy for its run. Workers work in the lead's own directory: the files they write there are the deliverables, and the lead reads them directly. The lead writes a self-contained brief with a definition of done, waits for the result (returned once, in a `<task_result>` envelope with a `task_id` that can resume the same worker), and integrates it; checking the lead's own output is never delegated. A worker started in the background returns immediately and wakes the lead with its result when it finishes. Workers cannot dispatch workers unless `subagent_depth` in `openscience.json` allows deeper nesting (default 1).

A delegated task shows as one line (what it is doing, which agent, its state and elapsed time) and streams nothing while it runs; open it for the result, its saved Results and **Open agent**, which shows the worker's own conversation. Stopping the lead also cancels its active delegated work. A stopped task's saved files and recorded tool results remain available.

Only the latest assistant message's text after its final tool call counts as the
result; earlier progress text cannot make an unfinished worker look complete. A
result without a Verification section (the command, its exit code, what it
proves) is a claim, and the lead is told so.

#### Subagent allowances

Bounded runs are **off by default**. Open **Settings → General → Subagents** and switch on **Enable bounded runs** to use budget and deadline controls for new conversations. When off, delegated tasks use their ordinary runtime without these extra limits. Model selection remains available in either mode.

The suggested defaults are **USD 5**, **1,000,000 tokens**, and **10 minutes**. The suggested increase amounts are **USD 1** and **250,000 tokens**. Edit these values before saving, or leave a numeric field blank to reset it to its suggested value. Changing the switch does not save until you choose **Save subagent defaults**.

A conversation keeps the mode chosen when its first subagent starts. Existing conversations with saved budgets remain bounded, even if you later switch the global default off. A conversation that started with bounded runs off stays off. Start a new conversation to use a changed mode. Within a bounded conversation, USD and token pools are shared by all workers of that root conversation. These limits do not cap the lead's own calls. Project configuration cannot enable or raise the user's global allowance.

With bounded runs on, a task receives an allocation from the approved pool. By default this is at most one quarter of the pool, capped at what remains. The lead can assign another amount within the unspent, unreserved balance. The default deadline is 10 minutes, including queueing and approval waits. Changing defaults affects new pools; it does not raise an existing pool.

USD uses the selected BYOK or Ace model's normal cost calculation. A local or custom proxy with configured prices also uses USD. Tokens include input, cache and output tokens for subscriptions and unpriced local routes; they are not the provider's weekly quota. Internal model calls owned by a worker count too. Search and compute keep their existing approval rules.

Before each call, the runtime estimates input and output separately at the selected speed and context prices. It counts image tokens separately from their encoded file size and includes the offered tool schemas. It reduces the output cap to fit that request inside the remaining allowance. New assignments can use the full work allowance; there is no automatic 75% wrap-up or reserved report call. Existing saved wrap-up contracts retain their final-call restriction until you continue them under a new assignment.

The runtime stops further calls when the allowance cannot cover them, cancels work at the hard deadline, and retains the actual stop reason, partial output and execution evidence. It does not start a separate summarization agent. A model response can end before a limit because of an error, cancellation, missing output or normal completion.

The main agent checks every result against its objective and expected output before using it. A completed worker run is not verified task completion. A limit-stopped worker can also have produced sufficient work. The main agent can proceed, use a partial result, inspect more saved evidence, continue the same child within approved funds, delegate again, stop or ask you for a pool increase. The worker's runtime reason remains unchanged when the main agent assesses the task result.

An allowance stop means another request cannot fit; it does not prove the grant was spent. Check recorded use and pending reservations. A request refused before dispatch adds no model usage. Definite authentication, validation and rate-limit rejections return their reserved allowance. Timeouts, conflicts and server errors remain uncertain, even with an empty body. Worker reports retain bounded excerpts of saved command output, including output captured before interruption. Long or partial output is marked incomplete. These receipts survive context compaction, so the main agent can check small command results even when the worker did not finish its report.

Open the task context panel to inspect the subagent allowance. **Continue with remaining allowance** resumes the same child. If you configured an increment, **Increase limit by … and continue** raises the pool once and resumes the child through a new Task call. **Stop here** keeps its files and conversation. An increase does not buy Wallet credits or reset a provider quota. A deliberate change of access route requires a new child; historical tokens are never converted into dollars.

The context-panel continuation assigns the available balance to the selected
worker. Existing sibling grants stay protected; new assignments may need to wait
until the continued worker returns unused allowance. The lead can instead use
Task to request a smaller allocation from the approved pool.

A nested worker also needs allowance from its parent. If that allocation is exhausted, continue the parent task first so it can receive and allocate more. Increasing the root pool alone does not renew the parent's allocation. Worker reports include a short accounting receipt for the lead, retained when the report is compacted.

The local server and its clients are trusted. These limits do not isolate
untrusted code running as your operating-system user. A shell or plugin that
can reach the control API can submit an allowance increase; code that can write
the app's state can modify its ledger. Revision checks prevent duplicate or stale
increases but do not prove human approval. Isolate untrusted execution from both
the control API and app state. A server bearer token alone does not separate
clients that already have that token.

Internal model calls owned by a bounded child use its pinned model and route.
They can therefore cost more than the configured small model. Internal calls
owned by the main agent keep the ordinary small-model selection.

An active or limit-stopped assignment keeps its model, reasoning variant and route when continued. A completed task can accept a deliberate follow-up with a different model on the same route. Revoked access stops it. Normal completion of the lead's response leaves background workers running; the explicit Stop action cancels its descendants.

Provider usage can arrive only after a call completes. The app bounds output where the provider supports it and admits calls conservatively. An already accepted request can exceed the local estimate, especially on subscription routes that do not accept output caps. The app records the overrun and blocks later calls. An uncertain request keeps its reserved allowance until there is usage evidence. This is a runtime inference allowance, not an exact provider invoice or a settled Wallet receipt.

Handoffs retain command receipt references and failures. A shell exit of zero
describes the outer process; it does not establish that nested tests passed or
that a scientific conclusion is valid. Those claims still need their actual
test or evaluation evidence.

The **Show reasoning and activity** control stays available during execution. Some
providers return tool activity without readable reasoning; OpenScience indicates that
state rather than presenting missing reasoning as an empty trace. A compute submission
receipt records its state at that moment; use **View current job** for its latest status.

## Action approval

Choose how much oversight you want from the composer's research controls. **Ask always**, **Ask risky**, and **Full access** offer progressively fewer routine approval prompts.

Keep your request specific about changes or costs you want to review. See [Permissions and control](/openscience/permissions) for choosing an approval mode and understanding a request.

## Persistent goals and progress

Use `/goal` for an objective you want to pursue across multiple steps:

```text
/goal Produce a reproducible analysis of data/samples.csv, with code,
a figure, a methods note, and a list of unresolved limitations.
```

The session header shows progress and context usage. `/checkpoint` captures a recovery point; `/handoff` saves a continuation note and compacts the conversation. Commands offered as skills must be enabled in your setup.

A persistent goal does not mean OpenScience can keep working while your computer or app is off. Save a checkpoint before interrupting a long task.

## Custom agents

Create a reusable specialist when you need a consistent role across projects:

```bash
openscience agent create
openscience agent list
```

The creation wizard produces a Markdown definition you can review and edit. Custom agents live in `.openscience/agent/` for a project or `~/.config/openscience/agent/` for your user account.

For a manually authored reviewer:

```markdown
---
description: Review analysis plans for confounding and data leakage
mode: primary
permission:
  edit: deny
  bash: deny
---

Review the analysis plan and identify unsupported assumptions.
Explain each concern and suggest a check before the analysis runs.
```

Save it as `analysis-reviewer.md` in the agent directory. Select it with `--agent analysis-reviewer`, or in the app: once a second primary agent exists, an agent chip appears beside the model control in the composer, and `Tab` in an empty composer cycles through the primary agents. A `primary` agent can lead a session, a `subagent` is for delegated tasks and the `@` menu, and `all` supports both.

Other frontmatter options: `model` (`provider/model-id`; Task workers follow the user subagent policy), `temperature` and `top_p`, `steps` (a cap on agentic iterations, after which the agent is asked to summarize and list what remains), `color` (a hex value or a theme color such as `accent`), `disable`, and `permission.task` globs that decide which workers the agent may dispatch. The deprecated `tools:` map still loads; `openscience agent create` writes `permission:` rules.

Custom definitions change the agent's instructions and permitted actions. Test a new profile on a small task before relying on it.

If only a background worker is cancelled, the lead receives its saved partial result and cancellation reason. Stopping the lead also stops its background workers and does not restart the lead to deliver those reports. Final usage can arrive after a stop; accounting updates preserve the original stop reason.
